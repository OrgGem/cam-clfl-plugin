# Security boundaries and limitations

The authenticated principal comes from a database-backed browser session or MCP bearer hash. Tool inputs never select the principal. Access uses explicit connection/account plus active connection/account availability, credential ownership or a grant, shared workspace membership and role. An administrator role alone does not permit another user's credentials. Upstream credential permissions remain an independent Cloudflare check.

Opaque MCP tokens use the authorization server's D1 as their issuer namespace; exact configured client, resource/audience, scope and expiry are checked on every request. Each deployment needs isolated D1 and keys. No Google token is accepted by `/mcp`. MCP access lasts one hour, browser login eight hours. Dynamic client registration and MCP refresh tokens are not implemented; configure a pre-registered client in ChatGPT. Third-party cookie/browser behavior and current ChatGPT OAuth compatibility require a live test.

All browser mutations validate Origin; cookies are HttpOnly, SameSite=Lax and Secure on HTTPS, with a `__Host-` cookie in HTTPS deployments. OAuth state is random, hashed, short-lived, single-use and browser-bound; Cloudflare state also binds app user and reconnect connection. PKCE is used on Google, Cloudflare and MCP code flows. Google JWT verification checks trusted JWKS, issuer, audience, expiry, nonce, verified email and subject. HTTPS and a single exact canonical origin are deployment requirements.

Credential ciphertext uses random-IV AES-256-GCM with connection ID as authenticated data. Secrets remain in Worker bindings; neither ciphertext, token bodies nor refresh errors are returned by APIs. Read adapters select output fields explicitly. DNS record content itself can contain sensitive TXT values: it is intentionally visible in previews and read results to authorized users, but not copied into audit events. Configure log retention/access accordingly.

Approvals are immutable operation references, bind actor/target/payload in D1, expire and are consumed once. The model cannot approve. Permissions and resource state are checked again at apply; upstream zone ownership is verified. API calls cannot be made atomic with an external permission revocation or a Cloudflare write by another client. A request already sent to Cloudflare may complete after a revocation. Subsequent requests are denied.

D1 atomically claims operations and serializes account/zone/name/type across connections. Write attempts are not automatically retried, even after a process crash. Replay only reads upstream. Readback matching the desired DNS state establishes the observed state, not attribution to a particular external actor; uncertain operations retain locks. Approvals/operations are scoped to the requesting user in this MVP. Cross-user/multi-level approvals and batch transactions are excluded.

Limits: 64 KiB incoming body, 2 MiB upstream JSON cap (64 KiB for OAuth), 15-second upstream timeout, 4 in-flight calls/connection with 30-second lease, bounded read pages, no authorization cache, no arbitrary upstream URL/path/tool execution. HTTP 429 and permission errors are sanitized; caller retries reads after backoff. The service does not claim a Cloudflare-wide rate-limit budget. App account/workspace spam and public registration quotas need operator policies before broad public release.

Audit is stored in D1 and is not a tamper-proof external ledger. Users see their own events. Connection owners also see events targeting their credentials. Workspace owners/admins can see another user's account events only with an explicit read grant on that account and current shared membership; a role alone does not expose private connection audit. Success and explicit lifecycle/grant actions are audited; rejected requests before an authenticated identity exists are returned with request IDs, not persisted as user audit records. A separate security logging sink may be appropriate for production, with header/body redaction.

Migrations are versioned and replay-safe through Wrangler's migration ledger; individual ALTER statements are not independently idempotent. Staging/live acceptance and backup restore rehearsals are release gates. No Free-tier capacity claim or production readiness assertion follows from local tests.
